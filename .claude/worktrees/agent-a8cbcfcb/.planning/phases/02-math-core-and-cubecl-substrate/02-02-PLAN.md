The module should contain:

**A. Launch configuration calculation:**
```rust
/// Calculate CubeCount and CubeDim for a 1D kernel over `np` grid points.
/// Uses 256 threads per workgroup (standard for compute kernels).
pub fn calculate_launch_config(np: usize) -> (CubeCount, CubeDim) {
    let cube_dim = CubeDim::new(256, 1, 1);
    if np == 0 {
        return (CubeCount::Static(0, 1, 1), cube_dim);
    }
    let num_cubes = ((np as u32) + 255) / 256;
    let cube_count = CubeCount::Static(num_cubes, 1, 1);
    (cube_count, cube_dim)
}
```

**B. Buffer management helpers:**
```rust
use cubecl_cpu::{CpuDevice, CpuRuntime};
use cubecl_core::prelude::*;

/// Create a CubeCL CPU compute client.
pub fn cpu_client() -> ComputeClient<CpuRuntime::Server, CpuRuntime::Channel> {
    let device = CpuDevice::default();
    ComputeClient::load(&device)
}

/// Upload an f64 slice to device memory, returning a handle.
pub fn create_input_buffer(client: &ComputeClient<...>, data: &[f64]) -> Handle {
    client.create(f64::as_bytes(data))
}

/// Create a zero-initialized output buffer of `n` f64 elements.
/// CRITICAL per Pitfall 4: output buffers MUST be zero-initialized
/// because kernels use += accumulation.
pub fn create_zero_output_buffer(client: &ComputeClient<...>, n: usize) -> Handle {
    let zeros = vec![0.0f64; n];
    client.create(f64::as_bytes(&zeros))
}

/// Read an f64 buffer back from device to host.
pub fn read_output_buffer(client: &ComputeClient<...>, handle: Handle, n: usize) -> Vec<f64> {
    let bytes = client.read_one(handle.binding());
    let result = f64::from_bytes(&bytes);
    result.to_vec()
}
```

NOTE on exact types: The `ComputeClient`, `Handle`, and return types from CubeCL have complex generic parameters. Claude's discretion on the exact type signatures — use type aliases if helpful. The key behaviors are: (1) create client, (2) upload data, (3) allocate zeros, (4) read back results. The exact CubeCL API surface (e.g., `client.create()` vs `client.create(bytemuck::cast_slice(...))`) should be determined by reading the cubecl docs/source.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Host -> CubeCL device | f64 data uploaded via bytemuck cast — must preserve bit patterns |
| CubeCL device -> Host | Result readback via f64::from_bytes — must preserve bit patterns |
| Kernel bounds | ABSOLUTE_POS can exceed array length in last workgroup |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-05 | T (Tampering) | kernel/launch.rs buffer creation | mitigate | Use bytemuck::cast_slice for safe byte conversion; verify round-trip identity in tests |
| T-02-06 | D (Denial of Service) | kernel/launch.rs zero-init | mitigate | create_zero_output_buffer allocates vec![0.0; n] to guarantee zero state — client.empty() returns uninitialized memory which would cause += to produce garbage |
| T-02-07 | E (Elevation of Privilege) | kernel bounds | mitigate | Every kernel MUST have `if ip >= output.len() { return; }` guard at top — CubeCount rounds up and excess threads would write out-of-bounds |
</threat_model>
