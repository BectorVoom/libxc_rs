<objective>
Modify the maple2c-to-Rust translation tools to generate incremental derivative
computation and shared preamble extraction. This is the core refactoring that will
dramatically reduce kernel code volume and build time.

## Background

Currently, each derivative order function (exc, vxc, fxc, kxc, lxc) is generated
as a standalone monolithic function that recomputes everything from scratch. For
example, in lda_c_pw:

- `func_exc_unpol`: computes t1-t89, writes tzk0
- `func_vxc_unpol`: recomputes t1-t89 identically, then adds t94-t154, writes tvrho0

The maple2c C source confirms this: vxc's body starts with an exact copy of exc's
let bindings. This pattern scales exponentially:
- exc: ~160 let bindings
- vxc: ~490 (all of exc + ~330 new)
- fxc: ~2,400 (all of vxc + ~1,900 new)
- kxc: ~15,000 (all of fxc + ~12,600 new)
- lxc: ~56,000 (all of kxc + ~41,000 new)

## Approach

Two complementary refactoring strategies:

### 1. Shared Preamble Extraction

Detect the common prefix of let bindings shared across ALL derivative orders for
a given (functional, spin). Extract these into a `#[cube]` helper function that
returns a struct of intermediates. All derivative order functions call this helper
instead of recomputing.

**Detection algorithm:**
1. Parse the compute lines for every derivative order of the same (functional, spin)
2. Walk the lines in order — while they are identical across all orders, they are
   "shared preamble"
3. The shared preamble ends at the first line that differs between orders, OR at
   the first output write variable

**Code generation:**
```rust
// Generated shared preamble struct
// (CubeCL doesn't support returning structs from #[cube] functions,
//  so we pass intermediate values via mutable Array<f64> buffers)

#[cube(launch_unchecked)]
fn lda_c_pw_preamble_unpol(
    rho: &Array<f64>,
    intermediates: &mut Array<f64>,  // packed t1..tN values
    // params...
) { ... }
```

### 2. Incremental Derivative Computation

Instead of each derivative level recomputing all lower-order work, generate code
where:
- `vxc` calls `exc` logic (or shared preamble) and adds only the vxc-specific terms
- `fxc` calls `vxc` logic and adds only the fxc-specific terms
- etc.

**Detection algorithm:**
1. For each (functional, spin), parse compute lines for consecutive orders
2. For (vxc, exc): find where vxc's lines diverge from exc's lines — everything
   before is shared, everything after is the "delta"
3. For (fxc, vxc): find where fxc's lines diverge from vxc's — the delta
4. Generate the delta as a separate function that receives the intermediates from
   the previous order

**Code generation pattern:**
```rust
// exc computes and writes energy
#[cube(launch_unchecked)]
fn func_exc_unpol(rho, zk, params...) {
    // preamble + exc-specific + write zk
}

// vxc reuses exc intermediates and adds derivative terms
#[cube(launch_unchecked)]
fn func_vxc_unpol(rho, zk, vrho, params...) {
    // preamble + exc-specific (shared with exc)
    // + vxc delta terms
    // + write zk and vrho
}
```

**CubeCL constraint:** `#[cube]` functions can call other `#[cube]` functions.
The key insight is that CubeCL inlines `#[cube]` calls at compile time, so there
is zero runtime overhead. We just need to structure the code so the proc macro
processes smaller units.

## Implementation Strategy

Modify each translator (translate_lda_v2.py, translate_gga.py, translate_mgga.py)
to:

1. Parse ALL derivative order function bodies for a given (functional, spin)
2. Compute the shared prefix (preamble) across all orders
3. Compute the incremental delta between consecutive orders
4. Generate:
   - A preamble helper function (shared computation)
   - Per-order delta functions (new computation for that order only)
   - A top-level per-order function that chains: preamble + lower deltas + own delta + output writes

This replaces one 56K-line function with ~6 functions of 1K-10K lines each.

## Validation

After modifying translators:
1. Re-translate ONE LDA functional (lda_c_pw) as proof of concept
2. Run oracle verification at 1e-12 to 1e-13 tolerance
3. If passes, proceed to batch re-translation in Plan 02

Output: Modified translator tools ready for batch re-translation.

   local variables. Since CubeCL #[cube] functions cannot return structs, the preamble

2. `exc_{spin}.rs` — Calls preamble, reads intermediates, computes exc-specific lines,

   PLUS the vxc-specific delta. This preserves the existing pattern where vxc writes
   both zk and vrho outputs. The key saving is that the shared preamble is a #[cube]
   function call that the proc macro processes once.

4. For fxc, kxc, lxc: same incremental pattern — each contains all previous levels'
   computation via #[cube] helper calls, plus its own delta.

**Alternative approach (simpler, still effective):**
Instead of passing intermediates via arrays, use the fact that CubeCL inlines #[cube]
calls. Generate helper functions that compute and return subsets of intermediates:

```rust
#[cube]
fn preamble_unpol(rho: &Array<f64>, ip: u32, ...) -> (f64, f64, f64, ...) {
    // shared computation
    (t1, t2, t3, ...)
}
```

**Important:** CubeCL #[cube] functions support returning tuples (up to a certain size).
If the preamble has too many intermediates for a tuple, split into multiple helper functions.

The key goal is: the proc macro processes each helper function ONCE, and the per-level
delta functions are small (hundreds to low thousands of lines, not tens of thousands).
