<objective>
Raise the per-`#[cube(launch_unchecked)]`-function split threshold in all three maple2c-to-Rust translators from 5,000 to 18,000 lines (CONTEXT D-06), then regenerate every kernel `.rs` file in LDA + GGA + MGGA using the new threshold (D-07). The 18K threshold sits 2,000 lines below the SPEC-locked 20K per-file cap (D-01), giving translator splits a safety margin while consolidating many existing `_partN_subM` files into fewer, larger ones. Operation order MUST be preserved across the regen — same `let` sequence and same output-write order — so the 1e-12 oracle parity contract from PROJECT.md/CLAUDE.md still holds (D-08). Sub-crate boundaries are NOT re-bin-packed (D-09); only intra-functional file content changes.

Purpose: Phase 9's narrowed scope (post-Round-4 SPEC) keeps the existing ~170 sub-crate split as a fait accompli but consolidates per-functional file fragmentation, which both reduces total file count under the relaxed 20K cap and produces fewer, larger compilation units that the dev machine handles within its proven memory headroom.

Output: Updated translators with SPLIT_THRESHOLD = 18000; regenerated kernel source trees in `crates/kernel-{lda,gga,mgga}*/src/`; verification log proving forward-guard cap (≤20,000 lines) holds; verification that no sub-crate Cargo.toml gained a `[profile.*]` section.
</objective>

**Why operation-order preservation matters (D-08):**
The translators emit `let` bindings whose left-to-right order matches the maple2c-translated C source. Floating-point addition is non-associative, so reordering `let t = a + b + c` into `let t = c + b + a` can flip ULPs and break the 1e-12 oracle parity contract. The split threshold change only shifts which `let` block lives in which `_partN` file; the linear order of operations within a function MUST stay identical.
</background>
