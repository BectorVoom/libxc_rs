<background>
**Requirement-ID mapping:**
- `SPEC-09-R1`: All 25 deferred GGAs compile at full derivative-order coverage AND produce 1e-12-parity-correct outputs. The compile-side was verified in 09-06; the parity side is verified here.
- Roadmap `BUILD-OPT-02` / `BUILD-OPT-03` deferred per CONTEXT D-05 — not claimed.

**Tolerance — strict 1e-12 (CONTEXT D-14):** Note this DEVIATES from `verify/tests/gga_oracle.rs`'s tiered tolerances (1e-12 for exc, 1e-10 vxc, 1e-8 fxc, 1e-6 kxc, 1e-4 lxc). For the Phase-9 phase-acceptance gate, the user has explicitly chosen strict 1e-12 across all orders (D-14). This is achievable because the operation-order-preservation invariant (D-08) is a byte-identity contract, not a numerical-tolerance contract — same op order produces bit-identical f64 (modulo CubeCL backend's own optimization passes). If a real numerical drift surfaces, that is a regression bug worth investigating, not a tolerance-relaxation candidate.

**Why a new test file (not extending `gga_oracle.rs`):**
- `gga_oracle.rs` uses tiered tolerances per the locked D-10-R policy from Phase 4; mixing strict-1e-12 logic into it would create per-test-case branching that is fragile to maintain.
- The Phase-9 test's job is short-lived: prove the regen didn't drift. After this plan signs off, the file is documentation of the post-Phase-9 baseline. Future regressions are caught by `gga_oracle.rs` at the standard tiered tolerances.
- A separate test file allows targeting it with `cargo test --test parity_phase09` without dragging in the rest of the verify suite.

**Test-system selection (CONTEXT D-14 + Claude Discretion):** The sweep must cover BOTH spin-zero (`H`, `Li`) and spin-polarized (`BrOH⁺`) cases at minimum. Recommended: use all 4 oracle test systems (H, Li, BrOH, BrOH⁺) for the deferred-GGA sweep so that any per-spin-mode regression surfaces; use a subset (H + BrOH⁺) for the MGGA spot-check to keep wall-clock manageable.

**Memory headroom and parallelism:** The parity sweep loads each functional's kernel (proc-macro-expanded code) once. Per CONTEXT D-08 memory headroom feedback, the dev machine has RAM headroom — but `cargo test --jobs N` with high N still risks OOM if multiple kernel-test compilation units run concurrently. Recommended: `cargo test --test parity_phase09 --release --jobs 3` (matching `.cargo/config.toml`'s `jobs = 3` policy). Inside the test, parallelize tuple iteration via `rayon::par_iter` if it does not blow up the per-thread proc-macro footprint (which it should not since proc-macro expansion happens at compile time, not test time). If rayon causes flakiness, fall back to serial iteration — correctness > speed.
</background>
