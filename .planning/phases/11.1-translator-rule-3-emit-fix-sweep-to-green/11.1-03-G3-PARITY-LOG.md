## How G3 was run (DEVIATION from plan-as-written — user-approved 2026-05-22)

The original Plan 03 ran G3 via `verify/tests/parity_phase11.rs::phase11_worst_case`, routing
mgga_c_b94 through `libxc_rs::eval::dispatch_mgga`. Investigation found this gate was **hollow
AND wasteful**:

1. **Built all 281 kernels for nothing.** `verify` depends on the `libxc_rs` umbrella crate
   (281 unconditional kernel deps, no `[features]`), so *any* verify test compiles the entire
   kernel tree — a multi-hour build that OOMs at the plan's `--jobs 3` on this 30 GB machine.
2. **Never evaluated mgga_c_b94.** b94 is in the deferred set and has NO dispatch arm
   (`MggaFunctional::from_id` lists ids 36…707, no 397/568), so even with
   `LIBXC_RS_BYPASS_DEFERRED=1` it returns `SkipNotRouted`. The entry also hard-coded id **568**
   (real libxc id is **397**, `xc_funcs.h:336`). The gate would have reported a meaningless pass.

**Rewrite:** a standalone crate `verify-canary/` (workspace member, NOT in default-members)
depending only on `libxc-kernel-mgga_c_b94` + `cubecl(cpu)` + `libxc-sys`. It launches the kernel
directly via a thin `#[cube(launch_unchecked)]` wrapper (the kernel is emitted as plain `#[cube]`
because it is unrouted — translator is routing-aware per quick task 260512-q01), and compares `zk`
to the libxc id=397 oracle. **Builds ONE kernel (seconds), and actually tests parity.**

## mgga_c_b94 status: **PASS** (1e-12, all 4 points)

## Root cause investigation (point 0) — user requested deep-dive

First run: pt1/2/3 matched to ~1e-13, but **pt0 (rho=0.1) diverged 2.3%**. Investigation
(decisive, evidence in `/tmp/b94_*.rs` + `/tmp/b94_oracle.c`):

- **BR89 exonerated.** libxc's `xc_mgga_x_br89_get_x(+0.135) = 2.0493763822653` — *identical* to
  the Rust kernel and a 200-iter bisection reference. The 60×-unroll Brent is correct (libxc uses
  a 500-iter cap; both converge to the same root). Same objective `x·e^{-2x/3} − rhs·(x−2)`.
- **A pure-Rust port of the kernel formula reproduced the kernel's pt0 value EXACTLY** — so the
  kernel faithfully implements the maple2c expression (which has identical structure to libxc's,
  no missing branch). No Rule-3-emit defect.
- **Root cause: the missing von Weizsäcker τ-clamp.** libxc's MGGA work driver enforces
  **τ ≥ τ_W = σ/(8ρ)** on the input before evaluating; the maple2c expression uses raw τ. pt0 was
  the only grid point with τ < τ_W (0.01 < 0.0125). Clamping τ→τ_W reproduced the oracle to
  6.3e-13. Validated on **4 distinct τ<τ_W points** (raw errors 4e-3…2.3e-2; all → ~5e-13 clamped;
  a control point with τ>τ_W unaffected).

## Fix applied

The von Weizsäcker clamp `τ = max(τ, σ/(8ρ))` is applied in the canary's host driver
(`tau_von_weizsacker` in `verify-canary/tests/g3_mgga_c_b94_parity.rs`), mirroring libxc's
`work_mgga` input preprocessing. With the clamp, G3 PASSES at 1e-12.

## Phase 11 hand-back (systemic finding, NOT 11.1 scope)

The Rust **production** path (`src/eval/mgga_dispatch`) does NOT replicate libxc's work-driver
input regularization (the τ_W clamp, and likely other `work_*.c` preprocessing). This is a
SYSTEMIC parity gap affecting **every** MGGA functional for inputs with τ < τ_W — squarely
re-opened Phase 11 / translator scope, not 11.1's narrow Rule-3-emit fix. Recorded in memory
`project_translator_missing_workmgga_tau_clamp` and handed back alongside G4.

## What G3 establishes

The translator Rule-3 emit fix (Plans 01/02) **preserved numerical correctness** on the canary:
the b94 maple2c expression evaluates bit-faithfully to libxc (≤6.3e-13) once inputs are
regularized the same way libxc regularizes them.
