# Quick Task 260509-q05 — Consolidate GGA + MGGA via tool fixes

## Why

User wants to "decrease GGA and MGGA kernels by changing tools". Same
spirit as q04 (LDA 4→2 via `--repack`), but the GGA/MGGA splitter tools
have bugs that prevent a clean re-bin-pack at the user's chosen
TARGET_MAX (100K, matching LDA q04 precedent).

Current state:
- GGA: **59** sub-crates (numeric + lettered: kernel-gga-1a, -1b, -3d, -4g, etc.)
- MGGA: **109** sub-crates (same shape)
- Smallest GGA sub-crate: 2,977 lines = 0.6% of TARGET_MAX=500000.
- Total GGA mass: 2,363,048 lines. Total MGGA mass: 4,691,012 lines.

At TARGET_MAX=100000 the bin-packer should produce ~24 GGA + ~47 MGGA
sub-crates.

## Tool fixes

### `tools/resplit_gga.py`

| Bug | Fix |
|-----|-----|
| `delete_old_subcrates()` regex `^kernel-gga-\d+$` misses lettered sub-crates (kernel-gga-1a, etc.) created by `split_oversized_kernel.py` | Broaden to `^kernel-gga-\d+[a-p]?$` |
| `update_workspace()` strip regex misses lettered | Same broadening |
| `get_functional_line_counts()` reads only from `kernel-gga/src/`. Currently empty (functionals all in lettered sub-crates) — tool would silently no-op | Add a "gather" phase: walk every `kernel-gga-*` sub-crate's `src/`, move per-functional dirs back into `kernel-gga/src/` before bin-packing |
| No `--dry-run` support | Add it; runs end-to-end accounting without filesystem mutation |

### `tools/rebatch_mgga.py`

| Bug | Fix |
|-----|-----|
| Generates Cargo.toml with stale `[profile.dev]` and `[profile.test]` sections — already removed elsewhere per recent commit "drop dead [profile.*] sections" | Drop them from the generated template |
| Does NOT update `kernel-mgga/Cargo.toml` deps — only PRINTS what user should paste | Auto-update the aggregator Cargo.toml |
| Does NOT update `kernel-mgga/src/lib.rs` re-exports — only PRINTS | Auto-update lib.rs |
| Does NOT update workspace `Cargo.toml` members — only PRINTS | Auto-update workspace |

## Tasks

1. Fix `tools/resplit_gga.py` (gather phase + broader regex + `--dry-run`).
2. Run `tools/resplit_gga.py --bin-limit 100000` live; verify GGA count drops to ~24 and `kernel-gga/src/lib.rs` re-exports all 131 functionals via the new numeric layout.
3. Fix `tools/rebatch_mgga.py` (drop profile sections; auto-update aggregator + workspace).
4. Run `tools/rebatch_mgga.py --target-max 100000` live; verify MGGA count drops to ~47 and aggregator + workspace are clean.
5. Commit: tool fix → execution per family (4 commits across 2 families). Then docs.

## must_haves

- truths:
  - GGA sub-crate count: 59 → ~24 (TARGET_MAX=100K).
  - MGGA sub-crate count: 109 → ~47 (TARGET_MAX=100K).
  - All 131 GGA + 92 MGGA functionals still re-exported from their aggregators.
  - No lettered `kernel-gga-Nx` or `kernel-mgga-Nx` sub-crates remain after.
  - Total line counts unchanged (only redistributed).
- artifacts:
  - Modified `tools/resplit_gga.py`, `tools/rebatch_mgga.py`.
  - Workspace `Cargo.toml` shrinks by (59-24)+(109-47) = 87 entries.
- key_links:
  - `tools/split_lda_subcrates.py` — q04 precedent (LDA 4→2).
  - `feedback_kernel_build_failure.md` — proc-macro OOM rationale.
  - `feedback_splitting_terminology.md` — "raise threshold ⇒ fewer bins".

## Out of scope

- `cargo check -p libxc-kernel-{gga,mgga}-{1..N}` to confirm no rustc OOM.
  Defer to user. Recovery if OOM: re-run repack at finer TARGET_MAX
  (e.g. 60K).

## Risks accepted

- Aggregator re-export shape changes from lettered (`batch1a`, `batch3d`)
  to numeric-only (`batch1`, `batch2`, ...). Any external code that imports
  e.g. `libxc_kernel_gga::batch3d` will break. Search confirms only the
  aggregator's own lib.rs uses these names, so the blast radius is internal.
- New, larger GGA/MGGA sub-crates may push proc-macro RAM past current
  budget. Recovery axis as in q04.
