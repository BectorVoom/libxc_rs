# Quick Task 260510-q01: Investigate cargo build OOM root cause and fix

## Goal

Identify why `cargo build` succeeds for some kernel sub-crates and fails with OOM for others, then apply the immediate fix so the previously-OOMing crates build under the project's RAM ceiling.

## Investigation summary

### Measurement

| crate     | LOC     | files | result                | peak RSS | wall   |
|-----------|---------|-------|-----------------------|----------|--------|
| math      | 3,491   | 15    | ✅ cached              | 86 MB    | 0.10s  |
| mgga-1    | 299,389 | 101   | ✅ this session        | 22.7 GB  | 23m30s |
| mgga-10   | 330,772 | 97    | ✅ pre-session (cache) | n/a      | n/a    |
| mgga-9    | 366,906 | 111   | ⚠ predicted ≥28 GB    | —        | —      |
| mgga-8    | 551,278 | 138   | ⚠ predicted ≥42 GB    | —        | —      |
| mgga-11   | 556,443 | 141   | ⚠ predicted ≥42 GB    | —        | —      |

System: 30 GB physical RAM + 8 GB swap → ~38 GB ceiling before OOM-kill. The 22.7 GB / 299K LOC measurement gives **~76 KB peak RSS per LOC** under the current toolchain (cubecl 0.10.0, RUST_MIN_STACK=1.87 GiB, codegen-units=16).

### Root cause #1 — solo-oversized functionals

`rebatch_mgga.py` bin-packs at FUNCTIONAL granularity. When a single functional's file size exceeds the bin budget it goes in a solo crate:

- `mgga_c_revtpss` (mgga-8): 551K LOC, 137 part files for one functional
- `mgga_c_tpssloc` (mgga-11): 556K LOC, 139 part files for one functional
- `mgga_c_rmggac` (mgga-9): 367K LOC, 109 part files for one functional
- `mgga_c_tpss` (mgga-10): 331K LOC — right at the edge, built successfully

The parts are already split inside the crate (each `lxc_pol_partN.rs` is one `#[cube] fn`), but **rustc compiles per crate, not per file** — every part's HIR/MIR/codegen artifacts coexist in memory. At 76 KB RSS/LOC, anything over ~330K LOC starts thrashing swap; over ~400K LOC it OOM-kills.

This matches the documented expectation in `tools/split_oversized_mgga.py`'s docstring: *"When a single functional exceeds 50K it goes in a solo crate; those solo crates OOM rustc during compile."* The threshold has crept up since that docstring was written, but the failure mode is unchanged.

### Root cause #2 — RUST_MIN_STACK typo

`.cargo/config.toml:17` was bumped in commit `ea5c51d2` (2026-04-20):

```diff
-# Default 8MB stack causes SIGSEGV; 64MB prevents stack overflow.
-RUST_MIN_STACK = "67108864"
+# rustc stack overflows (SIGSEGV); 64MB clears it with margin.
+RUST_MIN_STACK = "2010886400"
```

Comment claims "64MB". Value is 1.87 GiB (~30× the stated number). Each Rust thread (codegen-units=16 → 16 codegen threads + the proc-macro server thread) reserves up to 1.87 GiB of virtual stack; the macro-expansion thread for a 12K-line `#[cube] fn` recurses deeply enough to actually touch a meaningful fraction of that stack, contributing per-thread RSS that should never have grown past 64 MiB. Reverting to `67108864` restores fail-fast behavior on pathological recursion and reduces non-trivial RSS pressure during macro expansion.

### Already-applied / not-the-cause

- `tools/shrink_part_fanout.py` was already run: every `lxc_pol_part*.rs` in mgga-8/-9/-10/-11 uses `#[cube]` (not `#[cube(launch_unchecked)]`). That optimization is exhausted.
- `cubecl 0.10.0` upgrade (q01): not the cause — the same toolchain compiles 300K-bin crates fine.
- `jobs = 1` (.cargo/config.toml): not the cause — single-rustc, bounded by per-rustc RSS.
- `codegen-units = 16`: amplifies the RUST_MIN_STACK typo but not a root cause on its own.

## Fix

### Task A — Fix RUST_MIN_STACK typo

**files:** `.cargo/config.toml`
**action:** change `RUST_MIN_STACK = "2010886400"` to `RUST_MIN_STACK = "67108864"` (matches the in-tree comment "64MB clears it with margin").
**verify:** value matches comment; `python -c 'print(67108864/1024/1024)'` prints 64.0.
**done:** committed as a one-line config fix.

### Task B — Add --target-max parsing to split_oversized_mgga.py

**files:** `tools/split_oversized_mgga.py`
**action:** parse `--target-max N` in `main()` so the docstring matches behavior. Use the parsed value as TARGET_MAX for `find_oversized()` and `bin_pack()` instead of the module-level constant.
**verify:** `python3 tools/split_oversized_mgga.py --dry-run --target-max 350000` lists mgga-8, mgga-9, mgga-11 as oversized (and NOT mgga-10).
**done:** docstring no longer lies; `--target-max` is honored.

### Task C — Re-split solo-oversized MGGA crates

**files:** auto-generated under `crates/kernels/mgga-{8,9,11}{a,b,…}/`; updates to top-level `Cargo.toml` and `crates/kernels/mgga/{Cargo.toml,src/lib.rs}`; deletion of `crates/kernels/mgga-{8,9,11}/`.
**action:** `python3 tools/split_oversized_mgga.py --target-max 350000`. Threshold chosen so:
  - mgga-8 (551K), mgga-9 (367K), mgga-11 (556K) → split
  - mgga-10 (331K, builds ok) → left alone
  - new sub-crates target ≤280K LOC each → predicted peak RSS ≤22 GB (well under the 38 GB ceiling, with margin for the stack-typo fix to reduce RSS further)
**verify:** `git status` shows new mgga-{8a,8b,9a,9b,11a,11b} (or similar) directories; old mgga-{8,9,11} deleted; Cargo.toml workspace deps and members updated; `cargo metadata --no-deps -q` parses (i.e. workspace is well-formed). Build verification deferred to user per RAM-constrained-machine memory rule.
**done:** workspace metadata parses; per-crate LOC ≤350K confirmed via `find crates/kernels/mgga-* -name "*.rs" | xargs wc -l`.

## Out of scope

- Verifying mgga-{8a,8b,…} actually builds — RAM-constrained-machine rule defers cargo check/build to the user.
- Fixing the stale comment in `.cargo/config.toml` ("jobs=3 keeps peak under ~21 GB") — measurement shows even jobs=1 exceeds 21 GB on 300K-LOC crates, but the user's standing rule is jobs≤2 anyway and rewriting the comment is doc churn.
- Lowering codegen-units (would slow builds further) or changing rebatch_mgga.py's TARGET_MAX (would re-shuffle the multi-functional crates that already work).
- gga-8 (263K, 880 small functionals): not solo-oversized; current shape is fine.
