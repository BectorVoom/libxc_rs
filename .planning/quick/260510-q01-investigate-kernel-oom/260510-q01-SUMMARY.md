# Quick Task 260510-q01: Investigate cargo build OOM root cause and fix

## Outcome

Root cause identified, two contributing factors fixed:

1. **`RUST_MIN_STACK` typo** — `.cargo/config.toml` set the value to `2010886400` (1.87 GiB) while the comment claimed "64 MB clears it with margin". 30× over the intended size. Reverted to `67108864` (the value the comment describes, original pre-bump value).
2. **Solo-oversized MGGA crates** — three crates each contained a single functional whose split parts summed to ≥367K LOC, exceeding the system OOM ceiling at the project's measured per-LOC compile cost. Re-split via `tools/split_oversized_mgga.py --target-max 350000`:
   - `mgga-8` (mgga_c_revtpss, 551K) → `mgga-8a` (201K) + `mgga-8b` (350K)
   - `mgga-9` (mgga_c_rmggac, 367K) → `mgga-9a` (17K) + `mgga-9b` (350K)
   - `mgga-11` (mgga_c_tpssloc, 556K) → `mgga-11a` (350K) + `mgga-11b` (206K)

Two tool-correctness fixes were made along the way to make the splitter usable:
- `--target-max LINES` now actually parses (was promised in the docstring; only `--dry-run` was wired).
- Workspace-member path string updated from `crates/{crate}` to `crates/kernels/{crate}` (post-q07 layout).

## Diagnostic findings (root cause)

### #1 — Solo-oversized functionals

`rebatch_mgga.py` bin-packs at FUNCTIONAL granularity. When a single functional's parts sum above the bin budget it goes in a solo crate. Solo crates carry one functional's full HIR/MIR/codegen footprint into a single crate-scoped rustc invocation — and rustc compiles per crate, not per file. The translator-side per-file split inside the crate doesn't help the rustc memory peak because every file's HIR coexists in memory during a single crate compile.

The three solo crates that exceeded the ceiling all share the same shape: 4th-derivative kernels (`lxc_pol_part*.rs`) for MGGA correlation functionals (revtpss, rmggac, tpssloc). Each part is one `#[cube] fn` of 4–12K LOC. Numbers of parts per crate: 137, 109, 139.

The same pattern is documented in `tools/split_oversized_mgga.py`'s docstring as the design motivation for that tool. The threshold has crept up over time (50K → 500K) but the failure mode persists for any solo functional whose total parts exceed the system memory ceiling.

### #2 — RUST_MIN_STACK typo

`.cargo/config.toml:17` was bumped in commit `ea5c51d2` (2026-04-20) from `67108864` (64 MiB) to `2010886400` (1.87 GiB). The comment text remained "64MB clears it with margin" — the new value is 30× the stated size. Each Rust thread (with codegen-units=16, that's ~17 threads in a single rustc invocation) reserved that virtual stack. Linux's lazy stack allocation means RSS only grows as the thread touches deep frames — but the proc-macro expansion thread for a 12K-line `#[cube] fn` recurses deeply. The wrong value let it consume RSS far past the 64 MiB the comment expected. Reverting restores fail-fast on pathological recursion (SIGSEGV at 64 MiB) and reduces real RSS pressure during macro expansion on healthy crates.

### Already-applied / not-the-cause

- `tools/shrink_part_fanout.py` already ran on every part: `mgga-8/-9/-10/-11/*` use `#[cube]` (not `#[cube(launch_unchecked)]`). Optimization exhausted.
- `cubecl 0.10.0` upgrade (q01): not the cause — same toolchain compiles 300K-bin crates fine.
- `jobs = 1`: not the cause — even a single rustc exceeds the memory ceiling on solo-oversized crates.
- `codegen-units = 16`: amplifies the stack typo's per-thread cost but isn't a root cause on its own.

## Build verification

Per the standing memory rule (RAM-constrained machine; in-session cargo check/build is deferred to the user), no full build was run on the new sub-crates. The largest new bins (350K LOC) are predicted by linear extrapolation to peak ~26.6 GB pre-fix, comfortably under the 38 GB ceiling. After the RUST_MIN_STACK fix that prediction drops further. Operator verification step:

```bash
# Single-crate, single-job build of the heaviest new bin.
/usr/bin/time -v cargo build -p libxc-kernel-mgga-8b 2>&1 | tail -20
```

Expected: success, peak RSS 22–26 GB, wall ~25 min.
