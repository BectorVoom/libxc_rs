<objective>
Eliminate the rustc stack overflow that fires during `#[cube]` proc-macro expansion of mgga_c_tpssloc's nine flat-emit lxc_pol parts (7.9K-10K lines, single `#[cube] fn` each). Apply the free-helper `#[cube] fn` technique from `docs/manual/Cubecl/cubecl_macro_fanout_manual.md` at the **translator emit layer**, then regen only mgga_c_tpssloc and verify a single-crate `cargo build -p libxc-kernel-mgga_c_tpssloc` at `jobs=1` completes without a SIGSEGV / stack overflow.

Out of scope:
- Other D-LOCK-B exceptions (gga_c_ft97/lxc_pol, gga_c_gapc/lxc_pol, mgga_c_revtpss/kcis/kcisk/rmggac — keep the same translator change applicable but only regen + verify tpssloc here)
- Numeric correctness (Plan 11.1-03's G3/G4 covers parity; this quick task only proves compile)
- Full-tree regen (this task is scoped to one functional)
</objective>

<context>
**Symptom (per user 2026-05-19):** rustc stack overflow inside `#[cube]` proc-macro expansion when compiling one of the 9 oversized `mgga_c_tpssloc/src/lxc_pol/part{20,21,22,27,28,29,30,31,32}.rs` files. Each is a single `#[cube] fn <name>(...) { let t1 = ...; let t2 = ...; ... }` body with up to ~10,050 sequential `let`-bindings (measured on part21.rs).

**Why the splitter currently falls back to flat:** `tools/translate_v2/per_functional.py::_cse_chunk_part()` returns `None` when either the CSE wrapper itself OR any chunk-body stays over `split_threshold` (4500 lines). This happens for single-output 4th-derivative components (v4rho4_*, v4rho3sigma_*) because the cross-cut live-set runs to ~thousands of values; D-02 tuple-return ABI cannot subdivide them. Documented at per_functional.py:509-521 + tools/kernel_size_exceptions.txt header.

**Why this is the symptom now:** mgga_c_tpssloc was NOT in the 50-subcrate G1 sample sweep — its compile has never been measured. Phase 11.1 Plan 03 G4 (full-649 f32 oracle) requires it to compile.

**Reference:** `docs/manual/Cubecl/cubecl_macro_fanout_manual.md` §4-§8 — free `#[cube] fn` helpers with plain function calls reduce per-fn proc-macro expansion surface; CubeCL builds smaller IR per fn.
</context>

<approach>
**Linear block-helper partition at emit time.** When `_cse_chunk_part` would return `None` (CSE tuple ABI can't subdivide), don't fall back to a single-fn flat emit. Instead:

1. **Re-walk the straight-line body** in linear order, accumulating ~1000-1500 `let`-bindings per block (configurable: `FLAT_BLOCK_LINES`).
2. **Compute the live-set at each cut point** (vars assigned in prior blocks AND referenced in subsequent blocks).
3. **Emit each block as a free `#[cube] fn` helper** (`<func>_<level>_<spin>_part{idx}_<suffix>_block{N}`) returning the live-out tuple.
4. **Emit a thin entry `#[cube] fn`** (`<func>_<level>_<spin>_part{idx}_<suffix>`) that loads inputs, calls each block helper sequentially, threads the live set, and writes outputs.

This is the same shape as the existing CSE-chunked emit but driven by **byte/line count** instead of by output-set partition, so it works on single-output components where the tuple ABI fails.

**Key constraints:**
- Live-set arity at any cut should stay under ~200 (proc-macro fan-out budget for `CubeType` tuple returns). If a cut exceeds this, slide the cut point until the live-set narrows. If no cut achievable under the cap, fall back to flat for that block (logged warning).
- Each block-helper is plain `#[cube]`, NOT `#[cube(launch)]` (manual §4 — only the entry point ever launches).
- Wrapper calls block-helpers with concrete `::<f64>` turbofish (PATTERN.md Rule 9 concrete-caller form).
- Block-helper bodies are generic `<F: Float>` (PATTERN.md Rule 1).
</approach>

<risks>
- **Live-set arity blowup at every candidate cut point.** If even after sliding, no cut keeps live-set under 200, block-partition returns `None` and we fall back to flat — same situation as today. Mitigation: report which parts still flat-fall-back in the regen log; user decides whether to widen live-set cap or pursue a different strategy.
- **Sub-helper count explosion.** A 10K-line body split into 1500-line blocks yields ~7 helpers. The wrapper itself has ~7 sequential `let live_set_N = block{N}::<f64>(...);` calls — small. But if many functionals each generate dozens of helpers, the module tree grows. Mitigation: D-LOCK-D path-resolution audit unchanged; per-functional subcrate isolation (D-10) still applies.
- **Translator behavioral change touches every functional.** Even though we only regen mgga_c_tpssloc here, the translator is now able to invoke `_linear_block_partition` for any functional whose `_cse_chunk_part` returns `None`. To bound blast radius, the new code path is **opt-in via a CLI flag or env var initially** (e.g. `LIBXC_RS_TRANSLATOR_BLOCK_PARTITION=1`); flip default to ON only after the full-tree regen in a follow-up.
- **RUST_MIN_STACK might still be the bottleneck even after partition.** If the stack overflow is in a single `#[cube] fn` of <1500 lines (unlikely but possible), block partition won't help. Task 1 baseline tells us this BEFORE we commit to the fix shape.
- **User .cargo/config.toml currently has `jobs` commented out.** Cargo will use default parallelism (~all cores). Single-crate `-p` build limits cross-crate parallelism but dependency builds (cubecl, libxc-kernel-math) may still spike RAM. Reproducer must run at `jobs = 1` to isolate the per-fn macro expansion issue.
</risks>
