**Empirical anchor (do not re-measure):** baseline 25.4 GB peak; Path A 16 GB peak; 9 parts at 1497–3221 leaves each (max wrapper 9699 L). Target: peak < 12 GB.

**MAX_TUPLE_ARITY = 12 is the hard wall.** Live-set across any cut (leaf↔leaf today, leaf↔meta + meta↔meta tomorrow) must be ≤ 12. Same constraint the leaf chunker already solves at `cse.py` — applied one level up.
</context>

<approach>
**Hierarchical wrapper at the leaf-grouping layer of `_cse_chunk_part`.** When `LIBXC_RS_HIERARCHICAL_CSE` is set AND the wrapper would otherwise be > `split_threshold` lines (i.e. the case Path A's raised cap currently catches):

1. **Group consecutive leaves into meta-groups.** Walk the `wrapper_calls` list (which is already in leaf emission order) and greedily accumulate leaves into a meta-group while the meta's cross-meta live-set stays ≤ 12. Close the meta when adding the next leaf would push the live-set over 12, OR when the meta has reached `META_FANOUT` leaves (default 12). Live-set computation reuses the existing dep-graph: a leaf's outputs flow into the meta's outputs if any subsequent leaf (in a later meta) reads them OR if they appear in `output_writes`.

2. **Emit one `#[cube] fn meta{M}` per group**, returning a tuple of the meta's outputs (≤ 12 by construction). Each meta body is the existing leaf wrapper body for its slice (`let r_N = chunkN::<f64>(args);` lines), so ≤ ~13 sequential lets per meta + a tuple return.

3. **Top wrapper now calls metas instead of leaves.** For part21 (3221 leaves): ~270 meta calls × ~3 lines plumbing ≈ 810-line top wrapper. Per-meta body: ~13 lines. Per-leaf body: unchanged.

4. **Fall-back at the meta boundary, NOT in the whole pipeline.** If a meta cannot close under 12 outputs even at `META_FANOUT=1` (one leaf per meta still leaks > 12 outputs into future metas — implausible for the tpssloc shape but possible), emit a warning and return `None` from `_cse_chunk_part`. The existing chain (Path A raised cap → flat fallback) takes over. Do NOT try to be clever — log + return None.

5. **No `MAX_TUPLE_ARITY` change.** The 12-tuple cap is a CubeCL ABI fact (`cse.py:34` comment) — meta-grouping must respect it as-is.

**Three small per_functional.py extensions:**

- `META_FANOUT` constant (default 12; tunable via `LIBXC_RS_HIERARCHICAL_META_FANOUT` env).
- `_group_leaves_into_metas(wrapper_calls, var_to_chunk, downstream_reads, output_writes) -> List[MetaGroup] | None`: greedy grouper with live-set guard.
- A branch in `_cse_chunk_part` (after the leaf chunking is done, before the wrapper-cap check) that, when env-gated and oversized-wrapper-would-fire, runs the grouper and returns a hierarchical wrapper instead.

**One small emit.py extension:** accept a new part kind `cse-hier` carrying `{"wrapper": top, "metas": [{"wrapper": meta_src, "chunks": [...]}, ...]}`, writing `<output>/part{idx}/meta{M}/{chunk{N}.rs,mod.rs}` + `<output>/part{idx}/mod.rs`. The flat / cse kinds remain untouched.

**Why this is bounded:** per the previous SUMMARY's risk register, the only real risk is the 12-output live-set wall. The leaf chunker solves the equivalent problem at every cut today; we are applying the same algorithm one tier up on the same dep-graph data. If the grouper fails, the existing fallback chain catches us — no regression.
</approach>

<risks>
- **Live-set wall (≤ 12 cross-meta outputs).** Identified in `260520-a0c-SUMMARY.md` §Follow-up as the only real risk. Mitigation = the grouper's `None` return + fallback to existing Path A behavior. Code path is purely additive; cannot regress non-tpssloc functionals.
- **META_FANOUT=12 still leaves too much per-meta state.** Possible if each meta's body, while only 12 lines of `let r_N = ...`, still triggers cubecl-macros Scope/Context bloat. Out-of-this-session mitigation: lower to 8 or 6 via `LIBXC_RS_HIERARCHICAL_META_FANOUT` env. Plan does NOT loop within session.
- **Meta-wrapper itself is a `#[cube] fn` that gets `::<f64>` turbofish at call site.** Per PATTERN.md Rule 9/10 + memory `project_cubecl_turbofish_required`. Top wrapper calls metas with `::<f64>` (top is concrete-f64 from `&Array<f64>` inputs); meta calls leaves with `::<f64>` (meta is also concrete-f64 since its inputs descend from `&Array<f64>`). NO `::<F>` propagation issue here because the meta is NOT generic — it concretizes at the leaf boundary, identical to today's top→leaf call shape.
- **Cross-reference dependency: hierarchical mode requires `LIBXC_RS_ACCEPT_OVERSIZED_WRAPPER`.** The hier branch fires AFTER the wrapper-cap-check would-reject, so without the raised cap the branch is unreachable. Document in Task 2 step 1 (both env vars set). Future cleanup could make the hier branch self-sufficient, but that is a follow-up.
