## What landed (commit 2c7d3a0a48)

- `META_FANOUT_DEFAULT = 12` + `_meta_fanout()` (env-tunable via `LIBXC_RS_HIERARCHICAL_META_FANOUT`).
- `MetaGroup` dataclass bundling a meta's leaves / inputs / outputs / bind decls.
- `_group_leaves_into_metas(wrapper_calls, output_writes, ow_var_fn, meta_fanout)` — greedy
  grouper using right-to-left `future_consumers` walk (O(N) live-set computation). Honors

- `_build_meta_fn(...)` — emits one `#[cube] fn ..._meta{M}<F: Float>(...)` per group, calling

- `_build_hier_wrapper(...)` — top wrapper calling metas with `meta{M}::<f64>(...)`
  (PATTERN.md Rule 10 concrete→generic turbofish). Reuses the leaf-wrapper scaffolding

- Length-discriminant in `emit_functional` on the `cse_part` return: 2-tuple → existing `cse`

## Root cause — call-site gate defect

The hier branch was placed INSIDE the existing wrapper-cap-rejection block, at
`per_functional.py:911`:

```python
if wrapper_lines > wrapper_cap or max_chunk_lines > split_threshold:
    # 260520-c91 hierarchical branch — env-gated, additive.
    if os.environ.get("LIBXC_RS_HIERARCHICAL_CSE"):
        meta_groups = _group_leaves_into_metas(...)
        ...
```

The plan intended this to fire when the wrapper would otherwise be rejected. But the
predecessor's Path A (`LIBXC_RS_ACCEPT_OVERSIZED_WRAPPER=1`) raises `wrapper_cap` from
4500 → 15000 a few lines earlier:

```python
if os.environ.get("LIBXC_RS_ACCEPT_OVERSIZED_WRAPPER"):
    wrapper_cap = 15000  # above tpssloc's max 9699L wrapper
```

For mgga_c_tpssloc's worst part (part21):

| Quantity | Value | Gate impact |
|---|---|---|
| `wrapper_lines` | 9698 | ≤ 15000 → condition FALSE |
| `max_chunk_lines` | 28 | ≤ 4500 → condition FALSE |

→ rejection block is skipped → hier branch is unreachable → tpssloc emits as Path A's
flat-CSE shape (9698-line top wrapper, no meta layer).

The hier branch sits BEYOND a gate that Path A itself defeats. The Task 2 regen with both
env vars set (`LIBXC_RS_HIERARCHICAL_CSE=1 LIBXC_RS_ACCEPT_OVERSIZED_WRAPPER=1`) produced
**zero** `meta*` directories and a part21/mod.rs **identical** to the predecessor's
OOM-killed regen.

## Why this defect was not visible until Task 2

The plan's `<approach>` section described the hier branch as firing "after the leaf
chunking is done, before the wrapper-cap check" but the actual implementation placed it
**inside** the wrapper-cap-rejection block (the plan's wording was ambiguous: "before"
relative to which check?). Task 1's default-OFF verification used `gga_c_pbe` (a small
functional whose wrapper is well under the BASE 4500 cap, so it doesn't touch either
gate). Task 1's selftests exercise the grouper + emit paths in isolation. None of the
Task 1 gates exercise the actual call-site routing under tpssloc's specific conditions —
that only surfaces when you regen a functional whose wrapper sits between 4500 and 15000.

This is a textbook case of memory `project_phase11_structural_without_compile`: structural
selftests passed; the actual integration target's compile gate was never exercised.

### Phase 2 result — compile STILL OOMs but for a DIFFERENT reason

Single `cargo build -p libxc-kernel-mgga_c_tpssloc` at jobs=1:

```
   Compiling libxc-kernel-mgga_c_tpssloc v0.1.0 (...)
[ exit 137 — SIGKILL by kernel oom_killer ]
```

The kill arrived before `/usr/bin/time -v` could emit its post-mortem, so no peak RSS
line was captured.

**New failure mode** — aggregate rustc state across many small modules:

| Metric | HEAD (Path A) | Hier ON |
|---|---|---|
| Total `.rs` files in tpssloc crate | 30,795 | 63,360 (≈2×) |
| Top wrapper #[cube] fn size | up to 10K lines (OOM at per-fn expansion) | ≤ 2654 lines (per-fn fixed) |
| Per-`#[cube]-fn` macro RAM | Path A's ~16 GB on one 10K-line fn | bounded (small fns) |
| Aggregate rustc state under jobs=1 | already large | now larger — exceeds 30 GB |

Under jobs=1 + `cargo build -p libxc-kernel-mgga_c_tpssloc`, ONE rustc process compiles
the entire crate. It must parse + run `#[cube]` macros on + hold IR for ~63K modules
simultaneously, plus carry rustc's monomorphization table for `<F: Float>` trait-bound
generics across every one of them. That aggregate state, not any single fn's macro
expansion, is what now triggers oom_killer.

This is a fundamentally different bottleneck than the original Path A failure:

| Era | Bottleneck | RAM consumer |
|---|---|---|
| Pre-Path-A | per-fn macro state (one 10K-line `#[cube] fn`) | cubecl-macros 0.10 Scope + Context — ~25 GB |
| Path A landed (260520-a0c) | same as pre-Path-A but with cap raised so kernel doesn't reject | cubecl-macros 0.10 — ~16 GB |
| Hier landed (260520-c91 this session) | aggregate rustc parse+IR+monomorphization across 63K modules | rustc front-end — > 30 GB |

The hier fix did its job at the layer it targets. The compile budget is now bottlenecked
by a different layer entirely.

### Why META_FANOUT tuning cannot fix the new failure

The agreed single-retry budget (`META_FANOUT=8`) was **not used**, because the diagnosis
shows it would not help:

- **Lowering** META_FANOUT (8 or 4) → MORE metas → MORE files → makes aggregate worse.
- **Raising** META_FANOUT (24 or 48) → no-op for tpssloc, because `MAX_TUPLE_ARITY=12`
  live-set already caps effective meta size at ~4 leaves for dense 4th-derivative parts.

META_FANOUT is therefore neutral-or-worse for tpssloc; burning another OOM cycle would
have produced no information value.

### Next moves (architectural — deferred)

**Option A (recommended) — Workspace sub-crate split.** Split `mgga_c_tpssloc` into
multiple smaller workspace members at the part boundary (e.g. parts 0-50 in one sub-crate,
parts 51-110 in another). Each sub-crate compiles in its own rustc process, bounding
aggregate state. Mirrors the existing `mgga-1..mgga-14` repacking strategy that's already
in the project. Estimate: 1-2 hours.

**Option B — 3-tier hierarchical recursion (meta → super-meta → top).** Add another
wrapper tier so each level's `#[cube] fn` body AND total submodule count both stay
bounded. Would bring tpssloc's submodule count below the rustc aggregate threshold.
Estimate: 2-3 hours of translator work + a compile cycle.

**Option C — Status quo.** mgga_c_tpssloc stays deferred from `default-members`; Plan
11.1-03 G4 oracle gets a skip entry with rationale. Hierarchical CSE remains available
for non-tpssloc D-LOCK-B candidates (gga_c_ft97 lxc_pol, mgga_c_kcis/kcisk/revtpss/rmggac
lxc_pol, lda_c_pk09 kxc_pol) whose file counts are presumably smaller.
