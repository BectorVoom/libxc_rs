## How to handle generated.rs files across the modular workspace split

**Affects:** workspace-modular-split phase (target Phase 10)
**Logged:** 2026-05-07 via /gsd-explore

The libxc_rs codebase contains multiple build-script-generated source files
that will need to migrate into different target crates during the modular
split:

- `src/meta/generated.rs` and `src/meta/generated_propagation.rs` — large
  metadata tables for the 649 functionals, generated by `xtask`.
- `src/meta/generated_hybrid.rs` — hybrid-functional metadata.
- `src/registry/generated.rs` — registry lookup table.
- `src/compat/ids.rs` (if generated) — C ABI id <-> internal id mapping.

Questions to answer:

1. Which `xtask` codegen entry points produce these files, and what are
   their inputs (likely `libxc-master/` headers and `funcs_*.c` lists)?
2. After the split, do we generate **into the destination crate's `src/`**
   directly, or into a shared location and re-export? The first is cleaner
   but couples `xtask` to crate names; the second adds a layer of
   indirection.
3. Does any generated file mix concerns that span the new crate boundary?
   For example, does `meta/generated.rs` reference types that only exist
   in `libxc-core` while also being consumed by `libxc-compat` for the
   C ABI surface? If yes, the generator may need to be split.
4. What is the rebuild behavior? After the split, can a change to one
   functional's metadata trigger only a rebuild of `libxc-core` and
   `libxc-eval`, leaving `libxc-compat` untouched?
5. Should the generators move into a shared `libxc-codegen` crate inside
   `xtask/`, or remain as `xtask` subcommands that write into whichever
   crate's `src/` is targeted?

A 30-minute spike on the existing `xtask/` flow would resolve most of
these before planning the refactor.
