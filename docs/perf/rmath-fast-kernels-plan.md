# Plan: selective `rmath::fast` paths for generated kernels

Status: proposed  
Date: 2026-08-20  
Scope: CPU-only rayon kernels generated by `tools/translate_rayon/`

## Objective

Use the fast, vectorized math functions from the sibling `rmath` checkout at
`/home/user/Documents/workspace/rmath` to accelerate libm-heavy libxc kernels,
without weakening the project's public capability coverage, density screening,
or `1e-12` numerical agreement contract.

The optimization will be selective. It must not globally replace scalar libm
calls or the existing bit-exact SIMD functions. Each `(functional, order,
spin)` triple will be admitted independently after whole-kernel performance and
C-libxc parity measurements.

This plan deliberately retains the current exact implementation as the
baseline and rollback path. `rmath::fast` is a measured-accuracy approximation,
even though its `FullRange` policy handles special inputs. Per-call ULP bounds
are useful for screening candidates, but they do not prove that a derivative
formula will remain within `1e-12`; the formula may amplify a one-ULP input
change by orders of magnitude.

## Non-goals

- Do not change the maple2c formula structure or reorder arithmetic outside a
  replaced transcendental call.
- Do not enable fast math globally through compiler flags.
- Do not replace rayon, introduce a GPU production path, or introduce C/Fortran
  dependencies.
- Do not use `Fast + Finite` in the first implementation. The public
  `rmath::fast` wrappers use `Fast + FullRange`, which avoids adding unproven
  input-domain promises to libxc kernels.
- Do not hand-edit generated functional sources under
  `crates/kernels-rayon/{lda,gga,mgga}`.
- Do not remove the default-off CubeCL experiment in
  `crates/kernels-rayon/math`.

## Evidence and current state

CodeGraph traces the integration path as:

```text
maple2c C
  -> tools/translate_rayon/from_maple.py::translate_expr
  -> tools/translate_rayon/from_maple.py::emit_function
  -> tools/translate_rayon/simd.py::simd_body
  -> generated f64x8 kernel
  -> libxc-rkernel-math math facade
  -> current exact simd helpers or rmath::fast
  -> generated sweep and libxc-reval routing
```

The relevant seams are:

- `tools/translate_rayon/from_maple.py::SIMD_FUNCS`, which selects explicit
  SIMD per `(functional, order, spin)` triple.
- `tools/translate_rayon/simd.py::{FREE,UNARY,BINARY}`, which rewrites scalar
  calls into vector calls.
- `crates/kernels-rayon/math`, which is the single math dependency shared by
  all generated kernel crates and already re-exports `wide`.

The current explicit-SIMD allowlist contains these eight triples:

| functional | orders | spin | current math policy |
|---|---|---|---|
| `lda_c_vwn` | `exc`, `vxc` | unpolarized | exact exp/ln/cbrt plus approximate `wide` atan/tanh-class calls |
| `mgga_c_tpssloc` | `exc`, `vxc` | unpolarized | bit-exact exp/ln/sqrt/cbrt family |
| `mgga_c_scan` | `exc`, `vxc` | unpolarized | bit-exact exp/ln/sqrt/cbrt family |
| `mgga_c_rregtm` | `exc`, `vxc` | unpolarized | bit-exact exp/ln/sqrt/cbrt family |

There is an uncommitted partial dependency integration in the worktree. It
must be treated as user-owned work and reconciled rather than overwritten:

1. `crates/kernels-rayon/math/Cargo.toml` currently uses
   `path = "../../../rmath"`. From that manifest it resolves to
   `libxc_rs/rmath`, which does not exist. The requested sibling checkout is
   reached by `../../../../rmath`.
2. The partial edit removed the optional `cubecl` dependency and the crate's
   `[features]` section. That violates the project requirement that the
   default build contain zero CubeCL while
   `cargo test -p libxc-rkernel-math --features cubecl` remains available.
3. `Cargo.lock` was heavily pruned as a consequence. Lockfile changes must be
   regenerated and reviewed only after the feature graph is repaired.

## Proposed design

### 1. Keep exact and fast SIMD as separate policies

Replace the single conceptual allowlist with two disjoint sets:

```python
SIMD_EXACT_FUNCS = {
    # Existing approved triples.
}

SIMD_RMATH_FAST_FUNCS = {
    # Empty initially. Add only triples that pass all gates below.
}

assert SIMD_EXACT_FUNCS.isdisjoint(SIMD_RMATH_FAST_FUNCS)
```

`emit_function` will select a `math_mode` and pass it to `simd_body`. The SIMD
rewriter will use mode-specific mappings rather than changing every explicit
SIMD kernel at once. This gives three stable states:

1. ordinary scalar generated kernel;
2. explicit SIMD with the current exact helpers;
3. explicit SIMD with selected `rmath::fast` helpers.

The production source remains deterministic because the committed allowlists
choose exactly one state for each triple. During evaluation, a translator flag
or a small benchmark-only selection mechanism may generate exact and fast
variants without repeatedly editing the production allowlist.

### 2. Put a narrow rmath facade behind the math crate

The dependency should be explicit about the one required backend:

```toml
rmath = {
    path = "../../../../rmath",
    default-features = false,
    features = ["wide"],
}
```

The existing `wide = "1.6"`, optional `cubecl`, optional `bytemuck`, and
default-off feature definitions must remain. Cargo must resolve the `wide`
used by libxc and the `wide` for which rmath implements `Simd` to the same
crate version. `cargo tree -d` will enforce that assumption.

Expose a narrow name from `libxc-rkernel-math`, for example:

```rust
pub use rmath::fast as rmath_fast;
```

Generated kernels will import `libxc_rkernel_math::rmath_fast`; they should not
depend directly on the sibling crate or expose all of rmath through generated
crate manifests. This keeps the dependency boundary centralized and makes a
future rmath version update reviewable.

The local path is appropriate for this optimization campaign. Before a
portable release, replace it with a pinned Git revision, published version, or
vendored source so a checkout of `libxc_rs` does not depend on a sibling
directory being present.

### 3. Add explicit rmath call mappings

The first mapping set should cover:

| scalar spelling after translation | rmath fast spelling |
|---|---|
| `f64::exp(x)` | `rmath_fast::exp(x)` |
| `f64::ln(x)` | `rmath_fast::ln(x)` |
| `f64::exp_m1(x)` | `rmath_fast::expm1(x)` |
| `f64::ln_1p(x)` | `rmath_fast::log1p(x)` |
| `f64::atan(x)` | `rmath_fast::atan(x)` |
| `f64::tanh(x)` | `rmath_fast::tanh(x)` |
| `f64::sinh(x)` | `rmath_fast::sinh(x)` |
| `f64::cosh(x)` | `rmath_fast::cosh(x)` |
| `f64::asin(x)` | `rmath_fast::asin(x)` |
| `f64::acos(x)` | `rmath_fast::acos(x)` |
| `f64::powf(x, y)` | `rmath_fast::pow(x, y)` |
| `f64::atan2(y, x)` | `rmath_fast::atan2(y, x)` |
| translated `erf(x)` / `erfc(x)` | `rmath_fast::erf(x)` / `rmath_fast::erfc(x)` |

Keep these operations outside the rmath mapping:

- `abs`, comparisons, masks, and selection remain native vector operations.
- `sqrt` remains the `wide` operation because rmath cannot improve a single
  hardware square-root instruction.
- `pow_2`, `pow_3`, `pow_1_4`, and `pow_3_2` remain explicit algebra so their
  operation sequence does not change.
- The cube-root family initially remains on the current exact
  `libxc_rkernel_math::simd` helpers. If later admitted, each `pow_n_3` rewrite
  must evaluate `rmath_fast::cbrt` once and reuse the result. It must not
  duplicate the cube-root call when expanding `c*c` forms.

All rmath functions used in the grid loop must remain `#[inline(always)]`
through their call chain. An outlined function inside the loop is a rejection:
the existing measurements show that this destroys the vector schedule.

### 4. Preserve generated-kernel invariants

The rewrite may replace only the math call itself. It must preserve:

- maple2c statement order and expression grouping around the call;
- input and output strides;
- polarized component indexing;
- repeated-last-element tail padding;
- density screening and the `MIN_RUN` split/re-zero behavior;
- output zeroing per rayon chunk;
- zero heap allocation during repeated evaluation.

No optimization path may call a kernel body around `screened_call` or move
screening into a subset of functionals.

## Work phases

### Phase 0: repair and freeze the dependency baseline

1. Save the current dirty-worktree diff for review; do not discard unrelated
   edits.
2. Correct the rmath path and narrow its enabled features.
3. Restore the optional CubeCL dependency and feature definitions exactly as
   required by the existing `vector` module.
4. Regenerate `Cargo.lock` from the repaired manifest and inspect why every
   package changed. Optional CubeCL packages are expected to return to the
   lockfile even though they remain absent from the default build graph.
5. Verify:

   ```bash
   cargo metadata --no-deps
   cargo tree -p libxc-rkernel-math -e normal,features
   cargo tree -d
   cargo check -p libxc-rkernel-math
   cargo test -p libxc-rkernel-math --features cubecl
   ```

6. Confirm `cargo tree -e normal` on the default feature set reports no
   CubeCL package.

Deliverable: a compiling dependency baseline with no generated-kernel behavior
change.

### Phase 1: capture exact performance and numerical baselines

For each existing explicit-SIMD triple, record:

- single-thread ns/point;
- rayon sweep ns/point at the standard thread count;
- output fingerprint;
- worst absolute and relative error by output field against C libxc;
- NaN-vs-NaN count and finite mismatch count;
- allocation count;
- emitted inner-loop libm calls and vector width from disassembly.

Use the physical benchmark grid already employed by `bench-vs-libxc`. Add
focused input sets for:

- density-screened tails;
- values around the density threshold;
- vector lengths `0, 1, 2, 7, 8, 9, 15, 16, 17`;
- positive and negative zero, subnormals, infinities, and NaNs at the math
  adapter level;
- MGGA `tau` both safely above and close to the von Weizsaecker bound.

Do not use random independent MGGA arrays as the sole acceptance corpus;
out-of-domain points generate NaNs and do not establish physical parity.

Deliverable: a versioned baseline results table against which every fast
variant can be compared.

### Phase 2: implement and test policy-aware generation

1. Add exact/fast mode selection to `from_maple.py`.
2. Split `simd.py` mappings by math policy.
3. Emit `use libxc_rkernel_math::rmath_fast;` only for a fast kernel.
4. Update generated module comments so fingerprints that change are not
   incorrectly documented as bit-exact.
5. Add translator unit tests for:

   - every unary mapping;
   - `pow(x, y)` and `atan2(y, x)` argument order;
   - nested calls such as `exp(log1p(x))`;
   - calls inside `piecewise3` and `piecewise5` arms;
   - comparisons and masks surrounding a fast call;
   - identifiers containing a mapped name but not representing a call;
   - disjoint exact and fast allowlists;
   - one-time cube-root evaluation if that family is later enabled;
   - unchanged expression grouping outside the mapped call.

6. Compile-smoke one emitted kernel for unary, binary, special-function, tail,
   and polarized shapes.

Deliverable: generator support with an empty production fast allowlist.

### Phase 3: evaluate rmath fast functions in risk order

Evaluate one math family at a time, initially only in already-vectorized
triples. This isolates the effect of the math implementation from the effect
of introducing explicit SIMD.

1. `exp` and `ln` in the existing MGGA triples.
2. `exp`, `ln`, `atan`, and `tanh` in `lda_c_vwn`.
3. `powf` in the highest-sampled routed kernels.
4. `erf`/`erfc` in kernels where they contribute a material fraction of
   samples.
5. Remaining inverse-trigonometric and hyperbolic calls.
6. Cube-root family only after an isolated microbenchmark shows an advantage
   over the existing exact SIMD implementation.

For each experiment, build exact and fast forms from the same maple2c source
and compare them elementwise before comparing both to C libxc. Record the full
ULP distribution of the direct math result as diagnostic data, but make the
kernel output error the acceptance gate.

Deliverable: accepted and rejected candidate tables with measured reasons.

### Phase 4: expand beyond the existing explicit-SIMD list

After the first fast mappings are accepted, rank routed kernels by sampled
cycles in transcendental calls on a physical grid. Static call counts are only
a prefilter. For the highest-ranked triples:

1. Compare the normal scalar generated kernel with explicit SIMD exact math.
2. Compare explicit SIMD exact math with explicit SIMD rmath-fast math.
3. Admit explicit SIMD only if its complete load/compute/store loop wins;
   pure-arithmetic kernels often regress because LLVM already vectorizes them.
4. Admit the rmath-fast policy only if it separately clears the numerical and
   performance gates.

Polarized kernels and higher derivative orders are separate candidates. An
`exc` result does not authorize `vxc`, `fxc`, `kxc`, or `lxc`; derivative
expressions have different amplification and register pressure.

Deliverable: a minimal production `SIMD_RMATH_FAST_FUNCS` allowlist.

### Phase 5: regenerate and run the complete gates

Regenerate functional sources only through the translator:

```bash
python3 tools/translate_rayon/from_maple.py --all
```

Then run:

```bash
cargo test -p libxc-rkernel-math
cargo test -p libxc-rkernel-math --features cubecl
cargo test --release --manifest-path crates/kernels-rayon/oracle/Cargo.toml
cargo run --release -p libxc-reval --bin revalcheck
cargo run --release -p bench-vs-libxc --bin xcvs
```

Also run the relevant rmath accuracy suite from its own checkout, pinned to the
same revision used by libxc:

```bash
cargo test --release --test accuracy
```

The existing rayon oracle covers only unpolarized LDA/GGA. Therefore:

- every fast MGGA triple needs a targeted direct comparison with C libxc;
- every fast polarized triple needs a targeted direct comparison with C libxc;
- these targeted comparisons should be retained as regression tests, not run
  once and discarded.

Deliverable: regenerated sources and complete verification evidence.

### Phase 6: measure build and portability cost

`libxc-rkernel-math` is a dependency of all 266 generated kernel crates, so the
runtime win must not hide an unacceptable compilation expansion.

Measure:

- cold default workspace build wall time and peak RSS;
- incremental rebuild after changing one allowlist entry;
- release binary/code size;
- duplicate dependencies, especially `wide`;
- the default normal dependency tree;
- native AVX-512 performance on the reference Zen 5 machine;
- AVX2 compile and correctness behavior where hardware is available.

Use a separate target directory for cold-build comparisons instead of
destructively cleaning the shared cache, for example:

```bash
CARGO_TARGET_DIR=/tmp/libxc-rmath-fast-build cargo build --release \
  -p libxc-reval --timings
```

There is no runtime CPU dispatcher in this design. `wide` lowers according to
the compile-time target features, so non-AVX-512 builds must at least remain
correct and must not suffer a severe regression.

Deliverable: build-cost and portability measurements alongside runtime data.

### Phase 7: document and finalize

Update `docs/perf/simd-kernels.md` with:

- the exact rmath revision and license;
- compiler version, CPU, `RUSTFLAGS`, lane width, grid, and thread count;
- the final mapping set and production allowlist;
- accepted and rejected triples;
- exact-vs-fast and fast-vs-C error maxima by field;
- single-thread and rayon speedups;
- fingerprint changes expected from approximate math;
- build-time and dependency-tree impact;
- rollback instructions.

The lockfile review must be part of this phase. A reduced lockfile caused by
silently deleting the optional CubeCL feature is not an optimization result.

## Acceptance gates

A fast triple may be committed only when all applicable gates pass.

### Correctness

- Energy relative error remains within `1e-12` of C libxc on physical inputs.
- No new output field exceeds the oracle's tolerance, and no known offender is
  made worse without a separately approved bug fix.
- Finite mismatches, NaN-vs-NaN differences, signed zero changes, and infinity
  changes are reported separately.
- `revalcheck` gains no new chunked-vs-whole-grid differences beyond the
  documented pre-existing `gga_c_op_pw91` values.
- Density screening remains identical below the threshold.
- Tail lengths and mixed-lane special cases are correct.
- No public functional, order, spin, metadata path, or removed-ID diagnostic
  becomes unreachable.

### Performance

- The approximate fast variant reaches at least a 1.5x whole-kernel
  single-thread speedup over the current exact form. This retains the existing
  bar used when accepting a numerical divergence.
- The rayon sweep does not regress and shows a material improvement for the
  workload that motivated the triple.
- There are no heap allocations on the evaluation hot path.
- The optimized inner loop contains no outlined rmath or scalar libm call.
- Results are stable across repeated benchmark runs and reported with enough
  samples to distinguish the gain from noise.

### Build and dependency hygiene

- Default `cargo tree -e normal` contains no CubeCL.
- `cargo test -p libxc-rkernel-math --features cubecl` still works.
- `cargo tree -d` shows no incompatible duplicate `wide` versions.
- rmath remains pure Rust and introduces no C/Fortran production dependency.
- Cold and incremental build cost is measured and documented.
- Generated functional files are produced only by the translator.

## Stop conditions

Stop evaluating a candidate and leave it on the exact path when any of these is
true:

- whole-kernel speedup is below the 1.5x approximate-math bar;
- output error exceeds tolerance or varies unstably near physical boundaries;
- the fast path improves a microbenchmark but regresses the complete kernel;
- LLVM outlines the rmath call and the boundary cannot be removed cleanly;
- the change requires bypassing screening or assuming an unproved finite
  domain;
- the result depends on a CPU-specific behavior that cannot be kept correct on
  supported targets.

Rejected candidates and their measurements should be documented so the work is
not repeated after unrelated generator changes.

## Rollback strategy

The exact helpers and exact allowlist remain in the tree. Rolling back one fast
kernel consists of:

1. removing its triple from `SIMD_RMATH_FAST_FUNCS`;
2. returning it to `SIMD_EXACT_FUNCS` or ordinary scalar generation;
3. regenerating through `from_maple.py --all`;
4. rerunning the oracle, `revalcheck`, and fingerprint benchmark.

No public API or runtime configuration changes are needed for rollback.

## Completion criteria

This optimization campaign is complete when:

1. the rmath dependency is reproducible and the CubeCL optional feature is
   preserved;
2. exact and fast SIMD policies are explicit and covered by translator tests;
3. every production fast triple has retained benchmark and C-oracle evidence;
4. the generated tree, oracle, `revalcheck`, density screening, and allocation
   gates pass;
5. runtime, build-time, dependency, and portability results are documented;
6. rejected candidates and rollback instructions are recorded.
